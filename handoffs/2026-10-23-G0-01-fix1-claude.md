## 结果与范围（对应 Codex 的 4 点）

| Codex 指出的问题 | 原因 | 处理 |
| --- | --- | --- |
| 1. openScene 在真实 dev 上点了导航后等不到「シーンを検索」 | SSR 输出的按钮在 React 完成水合前没有绑定事件，测试点得太早；真实用户在慢网络下也会遇到第一次点击无效 | **就绪约定**：`app/page.tsx` 在挂载后设置 `<html data-app-ready="true">`；测试统一用 `gotoApp()` 等它出现，再点击（没有删断言，也没有加固定 sleep）。用户体验：水合超过约 0.6 秒时，导航和按钮会变淡、光标显示等待，而不是让点击悄悄失效 |
| 2. BASE_URL 下门禁测试仍按离线 harness 的 code 策略写 | 测试进程改 `process.env` 不会影响外部 Worker | helpers 先读外部服务的 `/api/access`：app / voice 套件在服务端用访问码时，凭 `CK_E2E_ACCESS_CODE` 先登录，否则立即报明原因；access 套件在服务端没有访问码时整体跳过，并写明原因；伪造 Host 的那条只在 harness 中运行（Vite 会先用自己的 HTML 403 拦截未知 Host，那不是应用的 403），且 403 必须带应用的 JSON code |
| 3. 离线 static 与 TS 5.9.3 不兼容 | `ignoreDeprecations:'6.0'` 只有 TS 6 接受；宽松 React 桩与已安装的真实类型冲突 | 优先使用项目自己的工具；仅在 TS ≥ 6 时才设置该选项；已安装真实 `@types/react` 时跳过 React 桩（组件以项目 `tsc --noEmit` 为准）。用一个伪造的 `@types/react` 验证了跳过分支 |
| 4. 离线模拟 8 项语音测试等数据通道超时 | 用 `unshare -rn`（只有 loopback 的网络命名空间）**复现了同一现象**：Chromium 根本不产生 ICE 候选。Codex 那边的环境是否也只有 loopback 尚未确认 | 超时时，报错会带上两端的 ICE 状态和候选，只有 loopback 时会明确标出这是环境限制；加了 `--allow-loopback-in-peer-connection`，但这对只有 loopback 的情况**无效**，仍需要普通网卡。GitHub 标准 runner 有普通网卡 |

另外修了一处在 BASE_URL 复测中才暴露的问题：原来猜码限流（每 10 分钟 10 次）把**正确**登录也算进去，同一 IP 多次正常登录会被锁定。现在只计错误的访问码，并新增了单元测试。
