## 1. COOKIE-ENCODING-001（提交 `89d8ad2c56c3eef2271b2a08c075259cd8e3f672`，在 PR #5 分支）

**原因**：32 字节 HMAC 编码成 43 个 base64url 字符，最后一个字符的低 2 位不承载数据。旧测试把末字符 A 改成 B，对某些 token 实际签名字节不变，于是「被篡改」的 cookie 仍被接受（Codex run 39978029073）。

**决定（token 契约）**：`verifyToken` 只接受规范 base64url，payload 和签名都要满足：字母表为 `A-Z a-z 0-9 - _`、无填充、未用位为 0、解码后再编码与原文一致；签名必须是 32 字节。理由是让每个有效 token 只有一种写法。**这只是加固，不是修复了已证实的绕过**：别名只能由已经有效签名的 token 改出来，不涉及未登录访问或伪造 payload。访问 cookie 和语音会话 token 共用这一函数。

**测试**：

| 文件 | 内容 |
| --- | --- |
| `prototype/tests/e2e/access.e2e.mjs` | 篡改时翻转签名第一个字节的 1 位，签名字节一定不同，期望 401；另外发送同字节的非规范别名（翻转末字符最低位，43 字符时总是未用位），期望 401。结果确定，不再随机 |
| `prototype/tests/unit/access-signing.test.mjs` | ① Codex 的固定夹具（假 secret，counter 14，末字符 A）：A/B 解码为相同的 32 字节，原 token 通过，别名被拒；② 两种 purpose 共 24 个 token：改字节、签名别名、payload 别名、填充、标准字母表都被拒；③ 规范解码器的边界情况 |

反向验证：在旧 `signing.ts` 上，改字节的检查通过，别名检查失败（e2e「a non-canonical alias of a valid cookie was accepted」；unit「signature alias accepted」）。
